# AIP — Agent Interaction Protocol · 0.3.0

## Scope and source of truth

AIP governs iterative ChatGPT collaboration on user-owned GitHub repositories. **This file is the single authoritative AIP instruction source.** Read and apply it at the start of each AIP run when accessible; if inaccessible, disclose that instead of claiming a refresh. Read component templates when needed. Avoid duplicate profiles, renderers, schemas or infrastructure.

## Architecture: views over external state

AIP is a presentation and interaction convention, **not** a system of record. Identity Header reads known repository/run context; GitHub Result presents retrieved GitHub data; Plan/Progress presents the agent's existing plan-tool or project-plan state; Proposal presents an agent-generated suggestion; Next Run conveys the user's selected intent. Components may offer interactions but do not own or persist the underlying work state. Use available authoritative tools and context, map their results to AIP views, and never invent unavailable state. Theme and temporary UI selection/input are ephemeral local presentation state, not project memory. Do not build a second plan database, GitHub cache, agent memory, adapters or synchronization layer.

## Response contract

1. Begin the **entire AIP response** with a **minimal theme-aware identity header**: `AIP · repository · branch/ref` (AIP version may be tiny secondary text or omitted from the visible header; it remains in handoff metadata). Its sole purpose is orientation: which assistant workflow, which repository, which branch. No commit, test status, explanation, badge or paragraph in this header; put verified results in GitHub Result instead. **Render this header exactly once at the top of the response, never as a subcomponent immediately above Next Run.** Between header and the final Next Run block, render the actual answer, relevant GitHub Result and/or Plan as needed; do not invent filler cards. Never invent a ref or result.
2. Use the contextual GitHub card family in `components/github-result/COMPONENT.md`: verified change results, open PR overview and branch overview. Choose only relevant views; ground all displayed GitHub facts in actual retrieved results. Distinguish completed, unverified and blocked work; never invent PR/branch state.
3. For multi-run work, use `components/plan-progress/COMPONENT.md` to show goal, numbered packages, concrete deliverables and grounded open/active/done/blocked status. Progress counts only verified completed packages. Plan rows may inform Next Run choices, but do not dispatch or persist anything by themselves. Prefer the agent's existing plan tool as source; do not copy its state into the handoff. End with a useful, curated set of interactive Next Run cards and, where worthwhile, agent improvement proposals. **No heading before those cards and no text after them.** Key `0` means continue agreed work. Do not offer filler actions.
4. Next Run uses the accepted hybrid template in `components/next-run/COMPONENT.md`: compact HTML choice cards with icon and title on one row, small visible action number in a corner, meaningful description and concrete expected deliverables, exclusive selection via outline/glow, one shared real HTML textarea that morphs from a 40px circular SVG icon when empty/unfocused into an expanded editable field on focus or when nonempty, and one accessible native icon-only Next Run pressable with the custom circular-arrow/play SVG from `assets/next-run.svg` beside it. Choose a meaningful single-digit number of cards, not a fixed three. The shared input may explicitly select an action using a leading valid `N:` prefix; keep the entire original input unchanged in `User instruction (verbatim)` and resolve the selected key consistently. Only the native Next Run pressable dispatches. User instructions take precedence over proposed task defaults within higher-priority constraints.
5. Choose the number and layout of suggestions deliberately, based on meaningful distinct actions and available space; do not pad to a fixed count, impose a hard cap of three, or force verbose cards into an awkward grid. Always consider `0 = Weiter` when continuing the current work is useful. Add genuinely distinct, actionable alternatives and proactive improvements when warranted; do not manufacture options for quantity. Prefer a manageable selection rather than an exhaustive catalog. Keep still-relevant unchosen options available in subsequent runs when context permits, without inventing persistence or claiming that they were saved. Use compact summaries with explicit deliverables; expand details only when needed. Proposal cards offer specific improvements prioritized by practical benefit and impact, with concise benefit/trade-off and one unboxed 👍 at top right. Clicking it authorizes implementation **in the next run** only. No implicit acceptance, ratings, voting or persistence.
6. Every dispatched next-run request follows [`prompts/next-run.md`](prompts/next-run.md): repository/ref, selected action/key, concise task, action parameters (including ephemeral theme), and the unchanged labeled `User instruction (verbatim)`. It conveys intent, **not** a plan snapshot, conversation history, GitHub inventory or agent memory. Include only essential external references when needed to disambiguate the action. Retain the AIP footer and AGENTS.md read instruction. When working on another user repository, reference this authoritative AIP source explicitly.
7. Text-only next-run dispatch cannot attach screenshots or other files. Never claim an HTML file picker can forward attachments through `GenUI.issueNewTurn`; ask the user to attach images in the regular chat composer when visual context is needed. Follow higher-priority host instructions and actual UI capabilities. Never claim tests or interactions succeeded unless verified.

## Visual themes

Use [`themes/themes.css`](themes/themes.css) as the single authoritative theme-token source for the identity header, Next Run, GitHub, Plan and Proposal cards. The approved morphing textarea uses the three-bar waveform + I-beam + separate lower arrow SVG, a circular cyan-accented idle shell and expanded editable state in Cyberpunk. The input shell may now use the chosen theme; keep ordinary text editing, selection, paste and focus semantics. The Next Run trigger must use a native DIL `<pressable>` for working dispatch and reliable SVG rendering; inline the custom circular-arrow/play SVG from `assets/next-run.svg` as its icon. Use its native background, border and radius props; AppBlock CSS cannot style it. Use an explicitly passed theme first; otherwise Pastel is the fallback. Cyberpunk and Neutral are available alternatives. AppBlock CSS can use scoped custom properties; native DIL cannot be globally styled by a CSS file. Theme changes appearance only, never status, data or actions. Apply the selected theme consistently across the top-level header, Next Run, GitHub, Plan and Proposal. **GitHub Result is not exempt**: use explicit token-mapped background, border, foreground and muted colors on all its example cards; avoid unthemed native defaults. See `components/github-result/COMPONENT.md`. Plan cards may be compact or detailed. A gate is a stop boundary with explicit type, evidence and status; a 'develop until gate' action must stop for local-only tests or human approval, and cannot advance blocked dependent packages without verified passage. See `components/plan-progress/COMPONENT.md`. Complex conditional branch graphs remain deferred.

Theme choice is ephemeral: use the incoming `theme` parameter when present, otherwise Pastel. The header gear owns theme selection; every themed component receives the same selected values. CSS custom properties can style scoped HTML/AppBlocks, but native DIL requires explicit token values. Theme must not change facts, actions or status semantics. No theme-specific README or parallel CSV table is needed.

## Accepted compact settings and input invariant

The identity header has a subtle classic gear icon (`settings`) at the far right. Its compact panel expands below the identity row and is collapsed by default. It only selects the visual theme (Pastel, Cyberpunk, Neutral). Apply the choice consistently to all theme-aware components in the current response and carry `theme` as a next-run parameter. No preference persistence, repository-default mutation, personal agent-rule controls, or extra settings features. The last explicitly passed theme takes precedence over the fallback Pastel default.

**Do not regress the Next Run input while rendering the settings panel.** Always retain the accepted shared real HTML morphing textarea: empty and unfocused = 40px circular waveform/I-beam/lower-arrow SVG; focus = smoothly expanded editable textarea; nonempty blur = remains expanded; empty blur = collapses. The separate native circular-arrow/play `<pressable>` dispatches the run. A plain always-visible DIL input/textarea is not an acceptable substitute. Consult `components/identity-header/COMPONENT.md` and `components/next-run/COMPONENT.md` together.

## Native UI component templates

Each component directory has a **COMPONENT.md** entry point describing its contract, usage and variants. Each component also has a `.dil` generation reference; Next Run additionally provides reusable HTML sources. Read `COMPONENT.md` for semantics and the referenced `.dil` for the rendering pattern. The `.dil` suffix is a repository convention, not an importable module or standalone compiler format. These are generation references, not importable modules. Use their structure, substitute concrete values and supply working callbacks. Do not invent a separate rendering layer.

- [`components/identity-header/COMPONENT.md`](components/identity-header/COMPONENT.md) — minimal themed AIP / repository / ref orientation strip.
- [`components/github-result/COMPONENT.md`](components/github-result/COMPONENT.md) — contextual GitHub cards: verified results, open PRs and branches.
- [`components/plan-progress/COMPONENT.md`](components/plan-progress/COMPONENT.md) — multi-run plan/progress display and next-run handoff.
- [`components/next-run/COMPONENT.md`](components/next-run/COMPONENT.md) — **accepted hybrid Next Run** visual and dispatch template.
- [`components/proposal/COMPONENT.md`](components/proposal/COMPONENT.md) — **experimental** optional improvement proposal with 👍 acceptance.

## Maintenance

Keep README descriptive, this file authoritative for behavior, `themes/themes.css` authoritative for token values, and component files focused on implementation. The single accepted Next Run component contract is `components/next-run/COMPONENT.md`, with `composition.dil`, `cards.html` and `input.html` as its reference sources; no competing experiment file. Avoid repeating this contract in each component. No standalone HTML renderer, JSON protocol, generic adapters, settings, exports or telemetry.
