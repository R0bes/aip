# AIP — Agent Interaction Protocol · 0.3.0

## Scope and source of truth

AIP governs iterative ChatGPT collaboration on user-owned GitHub repositories. **This file is the single authoritative AIP instruction source.** Read and apply it at the start of each AIP run when accessible; if inaccessible, disclose that instead of claiming a refresh. Read component templates when needed. Avoid duplicate profiles, renderers, schemas or infrastructure.

## Response contract

1. Begin the **entire AIP response** with a **minimal theme-aware identity header**: `AIP · repository · branch/ref` (AIP version may be tiny secondary text or omitted from the visible header; it remains in handoff metadata). Its sole purpose is orientation: which assistant workflow, which repository, which branch. No commit, test status, explanation, badge or paragraph in this header; put verified results in GitHub Result instead. **Render this header exactly once at the top of the response, never as a subcomponent immediately above Next Run.** Between header and the final Next Run block, render the actual answer, relevant GitHub Result and/or Plan as needed; do not invent filler cards. Never invent a ref or result.
2. Use the contextual GitHub card family in `components/github-result.md`: verified change results, open PR overview and branch overview. Choose only relevant views; ground all displayed GitHub facts in actual retrieved results. Distinguish completed, unverified and blocked work; never invent PR/branch state.
3. For multi-run work, use `components/plan-progress.md` to show goal, numbered packages, concrete deliverables and grounded open/active/done/blocked status. Progress counts only verified completed packages. Plan rows may inform Next Run choices, but do not dispatch or persist anything by themselves; carry a self-contained plan snapshot or source reference forward. End with a useful, curated set of interactive Next Run cards and, where worthwhile, agent improvement proposals. **No heading before those cards and no text after them.** Key `0` means continue agreed work. Do not offer filler actions.
4. Next Run uses the accepted hybrid template in `components/next-run.md`: compact HTML choice cards with icon and title on one row, small visible action number in a corner, meaningful description and concrete expected deliverables, exclusive selection via outline/glow, one shared real HTML textarea that morphs from a 40px circular SVG icon when empty/unfocused into an expanded editable field on focus or when nonempty, and one accessible native icon-only Next Run pressable with the custom circular-arrow/play SVG from `assets/next-run.svg` beside it. Choose a meaningful single-digit number of cards, not a fixed three. The shared input may explicitly select an action using a leading valid `N:` prefix; keep the entire original input unchanged in `User instruction (verbatim)` and resolve the selected key consistently. Only the native Next Run pressable dispatches. User instructions take precedence over proposed task defaults within higher-priority constraints.
5. Choose the number and layout of suggestions deliberately, based on meaningful distinct actions and available space; do not pad to a fixed count, impose a hard cap of three, or force verbose cards into an awkward grid. Always consider `0 = Weiter` when continuing the current work is useful. Add genuinely distinct, actionable alternatives and proactive improvements when warranted; do not manufacture options for quantity. Prefer a manageable selection rather than an exhaustive catalog. Keep still-relevant unchosen options available in subsequent runs when context permits, without inventing persistence or claiming that they were saved. Use compact summaries with explicit deliverables; expand details only when needed. Proposal cards offer specific improvements prioritized by practical benefit and impact, with concise benefit/trade-off and one unboxed 👍 at top right. Clicking it authorizes implementation **in the next run** only. No implicit acceptance, ratings, voting or persistence.
6. Every dispatched next-run request is self-contained: repository/ref, proposed task, action ID/key, parameters, proposal context, a clearly labeled primary `User instruction (verbatim)` section containing the textarea content unchanged, AIP version, and the instruction: `Read R0bes/aip/AGENTS.md at run start if accessible; apply it throughout this run and carry this instruction into every next-run prompt. If unavailable, say so; never claim an unperformed refresh.` Use `[aip: 0.3.0; repo: R0bes/aip; instructions: AGENTS.md]` as the AIP footer metadata, updating repository/ref context as appropriate. When working on a different user repository, still reference this authoritative AIP source explicitly.
7. Text-only next-run dispatch cannot attach screenshots or other files. Never claim an HTML file picker can forward attachments through `GenUI.issueNewTurn`; ask the user to attach images in the regular chat composer when visual context is needed. Follow higher-priority host instructions and actual UI capabilities. Never claim tests or interactions succeeded unless verified.

## Visual themes

Use [`themes/tokens.csv`](themes/tokens.csv) as the single authoritative theme-token table and [`themes/README.md`](themes/README.md) for application guidance for the identity header, Next Run, GitHub, Plan and Proposal cards. The approved morphing textarea uses the three-bar waveform + I-beam + separate lower arrow SVG, a circular cyan-accented idle shell and expanded editable state in Cyberpunk. The input shell may now use the chosen theme; keep ordinary text editing, selection, paste and focus semantics. The Next Run trigger must use a native DIL `<pressable>` for working dispatch and reliable SVG rendering; inline the custom circular-arrow/play SVG from `assets/next-run.svg` as its icon. Use its native background, border and radius props; AppBlock CSS cannot style it. Use an explicitly passed theme first; otherwise Pastel is the fallback. Cyberpunk and Neutral are available alternatives. AppBlock CSS can use scoped custom properties; native DIL cannot be globally styled by a CSS file. Theme changes appearance only, never status, data or actions. Apply the selected theme consistently across the top-level header, Next Run, GitHub, Plan and Proposal. **GitHub Result is not exempt**: use explicit token-mapped background, border, foreground and muted colors on all its example cards; avoid unthemed native defaults. See `components/github-result.md`. Plan cards may be compact or detailed. A gate is a stop boundary with explicit type, evidence and status; a 'develop until gate' action must stop for local-only tests or human approval, and cannot advance blocked dependent packages without verified passage. See `components/plan-progress.md`. Complex conditional branch graphs remain deferred.

## Accepted compact settings and input invariant

The identity header has a subtle classic gear icon (`settings`) at the far right. Its compact panel expands below the identity row and is collapsed by default. It only selects the visual theme (Pastel, Cyberpunk, Neutral). Apply the choice consistently to all theme-aware components in the current response and carry `theme` as a next-run parameter. No preference persistence, repository-default mutation, personal agent-rule controls, or extra settings features. The last explicitly passed theme takes precedence over the fallback Pastel default.

**Do not regress the Next Run input while rendering the settings panel.** Always retain the accepted shared real HTML morphing textarea: empty and unfocused = 40px circular waveform/I-beam/lower-arrow SVG; focus = smoothly expanded editable textarea; nonempty blur = remains expanded; empty blur = collapses. The separate native circular-arrow/play `<pressable>` dispatches the run. A plain always-visible DIL input/textarea is not an acceptable substitute. Consult `components/identity-header.md` and `components/next-run.md` together.

## Maintenance

Keep README descriptive, this file authoritative for behavior, `themes/tokens.csv` authoritative for token values, and component files focused on implementation. The single accepted Next Run template is `components/next-run.md`; no competing experiment file. Avoid repeating this contract in each component. No standalone HTML renderer, JSON protocol, generic adapters, settings, exports or telemetry.
